## Priority proposal

1. User reservation history and “my requests” read view, reusing existing authenticated identity and privacy projection only after a dedicated contract is verified.
2. Admin playback/Agent diagnostics and queue Undo, after proving exact ordering and owner-fence behavior.
3. Frequently used safe settings, one field group at a time, retaining PHP as writer until an equivalent Node owner is deliberately adopted.
4. Comments, favorites and public exports after identifying their storage and moderation boundaries.
5. Keep optional BINGO, OAuth/Drive, DDNS, backups/restores and legacy updater out of the main migration path unless operators request them.

### Node API convergence plan

1. Keep React User/Admin on same-origin Fastify `/api/v1`; all settings and business writes remain Fastify → MySQL.
2. Convert each required Legacy PHP User action into a narrow signed/session-aware HTTP compatibility call to Fastify. Preserve old page URLs, but do not run PHP → Fastify → PHP for the same business operation and do not restore SQLite writes.
3. Move search orchestration to a Node domain contract. Everything itself remains Windows-owned: Fastify can continue the current Agent job handoff, while PHP Everything/YukaLister adapters remain an explicit temporary fallback. Validate media-root allowlists before a selection can become a reservation.
4. Keep queue, participant attribution, request receipts/history, cancellation authorization, playback tasks/events and admin settings as explicit Node/MySQL owners. Do not treat nicknames as credentials or merge actor IDs by name.
5. Leave optional Bingo, comments-on-reservation, exports/import/restore and old player config PHP pages out of the main API surface until a requested workflow has a bounded replacement and a parity test.
