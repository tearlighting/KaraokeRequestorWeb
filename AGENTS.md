# Development rules

- `apps/user-web`, `apps/admin-web`, `apps/api-server` are the new TypeScript system; `legacy/php/` is compatibility code and the behavior reference. `packages/contracts/` owns shared wire contracts. See [migration/Owner matrix](docs/LEGACY_COMPATIBILITY.md) and [progress](docs/REFACTOR_PROGRESS.md).
- Inspect branch, index, untracked files and local changes first. Preserve user edits and runtime data; do not stage whole directories blindly. No automatic commit/push/force-push, `reset --hard`, volume deletion, real database recreation/schema migration or actual password changes.
- Prefer TypeScript for new features. Modify PHP for compatibility or PHP-owned modules only. Do not copy a PHP subsystem into TypeScript without behavior comparisons. Each module has one authoritative writer. A PHP Adapter call is not Node-native. Update the Owner matrix and compatibility tests whenever ownership changes.
- Keep `/api/v1` contracts compatible; validate inputs and domain outputs with Zod. Return `{ok:true,data}` or `{ok:false,error:{code,message,...}}`. Preserve actionable failures; never turn failures into empty success or retry uncertain Legacy writes.
- Authorize on the server, not in Vite. Preserve user/admin role and Origin separation, JSON/custom-header CSRF checks, HttpOnly sessions, nonempty legacy admin password and per-operation proof verification. Never trust caller role/IP headers. Bridge credentials are server-only; no credential/body logging or password persistence. Legacy Basic identity does not imply a Node session.
- Business ownership follows the current Owner matrix, not historical defaults. Phase 8 moves reservation creation/replacement to Node after equivalence tests. MySQL DDL is never run by the Fastify request process; Compose's one-shot `mysql-migrate` may apply ordered/checksummed SQL after the guarded `mysql-init`, under a MySQL advisory lock and before API startup. Preserve account passwords and existing data. PHP remains owner for search, metadata/lifecycle and unconverted legacy operations. Read-only adapters must not initialize DBs. SQLite paths are fixed/configured and WAL-aware; resolve paths explicitly, never from process CWD or browser input.
- Never expose or commit actual passwords, INI/runtime configuration, databases/journals, Bridge credentials, private keys, media, logs, node_modules/dist or test artifacts. `.gitignore` does not remove already tracked INI/PPK files; review index and diffs separately. Do not print raw configuration in diagnostics.
- Keep `origin` (tearlighting) and `upstream` (bee7813993) distinct. Analyze upstream changes before deciding whether to port to Node or retain Legacy; do not blindly overwrite Legacy or automatically merge/reset protected branches. Keep original PHP URLs available; avoid PHP 竊・Node 竊・PHP loops and duplicate writes.

## Commands (repository root; use npm.cmd in PowerShell)

```powershell
docker compose up -d --build
docker compose -f docker/compose.yaml exec -T web php /usr/local/bin/yukari-check-php.php /var/www/html
npm.cmd --prefix apps/api-server run typecheck
npm.cmd --prefix apps/api-server run build
npm.cmd --prefix apps/api-server test
npm.cmd --prefix apps/user-web run build
npm.cmd --prefix apps/user-web run test:e2e
npm.cmd --prefix apps/admin-web run build
npm.cmd --prefix apps/admin-web run test:e2e
```

All three apps have `typecheck`, `build`, `dev` scripts; install with `npm.cmd ci` in each app. Real regression tests require the synthetic isolated Compose deployment and installed Edge; test credentials must not enter traces. Never run write regression against deployed data; use the isolated test runbook below. User/admin Vite ports are 5173/5174, API 3000, Legacy 8180, bound locally. See [API runbook](apps/api-server/README.md) for environment configuration. For browser tests against an isolated API, set `API_PROXY_TARGET`, `E2E_API_BASE`, `E2E_PHP_BASE`, and `E2E_CONFIG_PATH` to that same synthetic deployment; Vite honors the process environment. Set `E2E_WEB_PORT` to a free test-only port instead of reusing an existing 5173/5174 server. Verify the proxy target before any browser test that writes.

Phase 5 historical SQLite behavior: Node originally owned the GET projection while PHP owned PUT. This was superseded in MySQL mode: current settings reads/writes go through Fastify and `app_setting`; Legacy PHP verifies current auth only. Keep the read-only config mount solely for authentication compatibility, and never log/return unrelated INI fields.

Phase 6: user/admin queue reads are Node-native; PHP remains the writer and owns initialization/WAL side-file lifecycle. Mount only `legacy/php/runtime/queue/` read-only to Node, never the whole Legacy tree. Legacy queue tickets are short-lived read-only capabilities, never Node admin sessions; preserve their signature, Origin, UA and policy-revocation checks. Runtime DB relocation requires explicit approval and stopped writers with hash verification.

Phase 7: administrator delete/up/down/warikomi are Node-owned in Compose (`YUKARI_NODE_QUEUE_MUTATIONS=1`). Mount **only the dedicated queue directory** read/write; PHP and non-root Node share group 33. PHP still owns reservation creation/automatic placement, metadata/lifecycle, settings and playback writes. Notification-only PHP reuse is not a PHP queue writer. Preserve explicit committed-but-not-notified errors; never replay a committed mutation. Migrated Legacy HTTP writes fail 410 before bootstrap; do not restore them or grant write access with read tickets. See the Phase 7 matrix for the intentionally closed bulk/restore paths.

Phase 7 write regression must use synthetic `docker/compose.isolated.yaml` and `E2E_CONFIG_PATH`, not the deployed database, even with cleanup. See [isolated test runbook](docs/LEGACY_COMPATIBILITY.md#phase-7-isolated-test-runbook). Never run host Windows and container Linux SQLite simultaneously on the same WAL fixture; cross-runtime tests run both writers in Linux containers.

Phase 8 historical SQLite behavior: reservations/receipts originally shared the queue SQLite database. In MySQL mode the current owner is Fastify/MySQL (`reservation` + `request_submission`), and Legacy `exec.php` forwards through the authenticated adapter; never restore SQLite as a fallback. Reuse the same receipt to resolve uncertain responses; never send it in URLs/logs. Core reservation/history/receipt writes are atomic; notification is post-commit and may return a committed-but-not-notified error.

Phase 9 Player Agent runs on the Windows host, never in Docker. Set `MPV_PATH` to the explicit executable; never require global `PATH`. Agent Bearer credentials are independent of user/admin sessions; only admin sessions can create/control tasks, and public playback status is sanitized. Keep task state in its separate Player Agent volume; do not add queue SQLite schema or update `nowplaying` from the test-player workflow. Agent media paths must resolve beneath its configured host media root; spawn the configured mpv executable with fixed arguments and `shell:false`. Use mpv's local JSON IPC for observed playback state/end-file events; do not infer `playing`/`completed` from process launch, duration, timers, or keyboard simulation. The Agent may connect idle without `PLAYER_TEST_VIDEO`; do not create a test task until a real media file is configured beneath `PLAYER_MEDIA_ROOT`. Host setup/validation: [Player Agent README](agents/player-agent/README.md).

Phase 10 historical SQLite design was superseded by Phase 16. Current formal autoplay, when separately enabled, uses MySQL `playback_task`, append-only `playback_event`, and `reservation`; the JSON volume is only test tasks/Agent heartbeat. `YUKARI_NODE_AUTOPLAY=0` stays the default and this repository's Compose setting must remain off absent explicit approval. Fastify is the sole queue consumer. Existing Legacy playback is disabled/guarded in MySQL mode. State projection and task transitions commit in one MySQL transaction; `playing` requires observed mpv playback and `completed` requires real EOF. Agent leases/restart recovery fail closed as uncertain and never replay or infer completion. Admin history omits paths and credentials. Unsupported kinds/options fail without rewriting the reservation.

Phase 12 mode-2 manual start applies only to the earlier SQLite scheduler and is not available in MySQL mode. Current MySQL playback accepts FIFO mode 1 only; modes 2–5 fail closed until migrated and tested. Never rewrite saved mode values to make Node eligible. Before any owner handoff, reject existing Legacy active markers. For Docker POSIX media paths, configure `PLAYER_PATH_MAPPINGS` explicitly and constrain targets beneath `PLAYER_MEDIA_ROOT`; never infer paths from names.

Phase 13 local operation uses `scripts/windows/Start-Yukari.cmd`, `Stop-Yukari.cmd`, `Get-YukariStatus.cmd`, `Show-YukariLogs.cmd`, and `Configure-PlayerAgent.cmd`. Static production React is built into the Apache image at `/user/` and `/admin/`; `/app/` is the local portal and original PHP paths stay unchanged. Vite remains a separate dev server. The Agent's path-only config belongs under `%LOCALAPPDATA%\YukariPlayerAgent`; never store its credential there. Stop only the recorded Agent through its local pipe and Compose `web`/`api-server`; never kill all Node processes or remove volumes. Full instructions: [Windows runbook](docs/WINDOWS_LOCAL_RUNBOOK.zh-CN.md).

For browser tests, use each app's `npm.cmd ... run test:e2e`; `scripts/run-web-e2e.mjs` owns the exact Vite child so Windows teardown is deterministic. Set `E2E_WEB_PORT` to avoid developer servers, or set `E2E_BASE_URL` and `E2E_APP_PATH` to test the built Apache routes.

Phase 15 web foundations: `packages/theme/` and `packages/language/` own the user's theme/language managers and dictionaries; `packages/reactiveStore/` bridges Vue reactivity to React with `useSyncExternalStore`. Both web apps consume those shared managers through small app-local store exports; page-specific state belongs in feature/page stores where it is shared or needs coordinated updates. `packages/web-foundation/` is limited to presentation primitives and compatibility re-exports. Keep user/admin route trees independent (`/user/` and `/admin/` in production; Vite root in development), preserve protected admin session checks, and keep Apache SPA fallbacks scoped to those two prefixes so `/app/` and Legacy PHP URLs continue to resolve. Locale defaults to Japanese; translations must not alter user-entered song/singer/comment data. Theme and locale preferences are local browser preferences, not server settings. Keep framework/runtime dependencies installed per app; do not rely on a repository-root `node_modules`. Run each web app's typecheck/build/E2E scripts after changing shared foundations; Phase 15 visual/router screenshots belong in ignored `.local/phase15-shots/`.


Phase 16 MySQL boundary: when `MYSQL_HOST` is set, Fastify owns reservations, receipts, queue mutations, settings, and formal playback tasks/events in MySQL. Do not fall back to SQLite on MySQL errors. Old SQLite data/volumes/backups are retained and are not an alternate write target. Legacy search and authentication proof remain PHP-owned; MySQL mode disables the old SQLite notification counter instead of calling it. Compose runs marker-gated `mysql-init` and ordered `mysql-migrate` one-shots after MySQL is healthy and before Fastify. Existing app/viewer passwords and settings are not reset or re-imported; the migration user has bounded schema privileges and the API never runs DDL. A migration failure gates API startup, and an active playback task blocks deployment. MySQL ports bind to loopback. Compose has local-development-only fallback credentials; `.env` may override them and must never be used as production credentials. Keep autoplay disabled unless separately authorized.

Phase 19 settings ownership: `app_setting` in MySQL is authoritative. React Admin writes only through Fastify with revision checks; do not restore PHP `init.php` or `api/admin.php` as a settings writer. Queue auto-order options (`request_automove`, reset, midjoin) must be read from MySQL for every new Node reservation; PHP Bridge copies of these values are compatibility context only. Their additive values are seeded only by explicit setup/bootstrap (`docker compose --profile setup ...`), never silently at API startup. MySQL playback currently supports FIFO mode 1 only; modes 2–5 must remain unavailable unless implemented and behavior-tested. Keep `YUKARI_NODE_AUTOPLAY=0` by default and show the exact deployment/Agent blocker in Admin. `startvolume` and Legacy SSE refresh are read-only compatibility values until the current mpv/React runtime actually applies them; reject misleading writes. See [Legacy Admin settings audit](docs/LEGACY_ADMIN_SETTINGS_AUDIT.zh-CN.md).

Phase 20 mpv controls: Fastify authorizes each Admin command and binds it to the current task and authenticated Agent. The Windows Agent accepts only typed seek, volume, mute, audio-track ID, subtitle-track ID/off, and bounded ±6-semitone pitch operations over its private mpv IPC; never expose arbitrary IPC or shell execution. Reservation `keychange` is stored in the existing MySQL reservation field and applied by Agent before playback resumes; nonzero key requests fail closed if the Rubber Band filter is unavailable. mpv telemetry is an Agent heartbeat snapshot, with only a media basename and sanitized track labels; it is not a queue transition and must not write MySQL. Admin live polling reads this snapshot separately from slower task/status reads. Keep Agent connectivity, mpv IPC state, and MySQL queue task state distinct. Only real mpv EOF may complete a task; stop, skip, error, and disconnect remain different outcomes. Audio track selection is not pitch shift; tempo remains unsupported.

Phase 16 MySQL-mode Legacy SQLite retirement: normal Compose bakes PHP source into the web image and mounts only `config.ini` read-only, the dedicated `List.sqlite3` location read-only, and a separate shared autoplay-owner fence volume. It does not mount the business queue directory or repository workspace into PHP or Node. `YUKARI_MYSQL_MODE=1` skips request DB initialization, suppresses priority DB and search-history writes, and the Apache `mysql-mode-guard.php` allowlist disables unmigrated PHP business pages with 410. Search, authentication, Bridge contexts, and signed `exec.php` 竊・Fastify compatibility requests remain allowed. MyPage/favorites/pairing/comments/Bingo/not-found/legacy admin/player/settings/update/restore routes are disabled. The PHP entrypoint does not start `queue-wal-anchor.php` in MySQL mode; keep it only for isolated SQLite compatibility tests. MySQL schema-only tables (`saved_song`, `favorite_keyword`, `pair_code`, `external_identity`) are not evidence their Legacy features use MySQL. For Docker-host Everything access, PHP may use `YUKARI_EVERYTHING_HOST`; Compose maps `host.docker.internal`, but the operator must enable/verify Everything HTTP Server and Windows Firewall access. The current `List.sqlite3` is zero-byte/uninitialized, so YukaLister capability reports unavailable until a valid read-only index is supplied. No production search availability is implied by HTTP 200 or DNS mapping.

Phase 25 participant identity: a user session's stable `userid` remains the browser actor/authorization identity; `app_user.userid` is a distinct participant profile ID and its nickname is only a display label, never authentication. React may submit a selected existing `participantId`; Fastify verifies it exists and stores it in `reservation.participant_userid`, while `request_submission.owner_id` and `request_history.userid` remain the actual session actor. Do not merge users by matching nicknames, grant edit/delete rights through participant selection, or rewrite past `reservation.singer` values during a rename. The additive migration leaves older reservations unlinked (`NULL`) rather than guessing attribution. User/Admin participant APIs require their normal server sessions; names/IDs returned by the user choices endpoint do not grant permissions. See the Phase 25 Owner matrix for deployment/migration status.

Phase 17 Media Agent search: React Everything queries may be routed through Fastify to the authenticated Windows Agent (`YUKARI_AGENT_SEARCH=1`). The Agent polls bounded search jobs, queries only the configured Everything HTTP endpoint, caps results/timeouts, and realpath-checks every result beneath `PLAYER_MEDIA_ROOT`. Browser results carry user-bound, expiring `media:<id>` references; reservation writes resolve those references server-side to the Agent-verified path. Never return absolute host paths to browsers or accept arbitrary Agent URLs/commands from clients. Keep the Compose switch at `0` until an actual indexed media hit is verified; `0` retains the PHP Everything compatibility path, while `1` returns explicit offline/search errors rather than falling back silently. The Agent reports sanitized Everything/media-root/player health. Lock files include a PID; remove stale locks only after confirming the owner process exited. Never clear an unverifiable legacy lock.

Phase 18 Windows launcher: Admin may request only fixed `start`/`stop` actions through authenticated Fastify routes. A per-user Windows launcher polls with the existing Agent credential and starts only the built `agents/player-agent/dist/main.js` using the current Node executable, fixed arguments and `shell:false`; it never accepts shell text or arbitrary paths from the browser/API. It reuses a connected authenticated Agent, refuses unverifiable/live stale locks, waits for active playback to stop safely before graceful Agent shutdown, and remains idle/retries while Fastify is unavailable. The browser closing does not stop it. `Start-Yukari.cmd` starts/reuses the fixed Launcher hidden after Compose is ready; it does not start the Agent directly. Admin → System then starts/stops the Agent. `Start-PlayerAgentLauncher.ps1` safely verifies an existing lock and writes logs under `%LOCALAPPDATA%\YukariPlayerAgent\logs`. A per-user interactive logon task is optional; dry-run is the default for `Install-PlayerAgentLauncher.ps1`. Remove only that named task with `Uninstall-PlayerAgentLauncher.ps1`; inspect it with `Get-PlayerAgentLauncherStatus.ps1`. The Launcher is not a Windows Service and must not kill processes by image name. Autoplay remains independently disabled unless explicitly authorized.

### Phase 19B current behavior (supersedes earlier Phase 19 notes)

In MySQL deployments, Admin settings are React → Fastify → `app_setting`. The supported Node strategies are mode 1 (explicitly armed FIFO with EOF advance) and mode 2 (explicitly armed manual, one Admin start per song). Mode saves do not arm playback. `scheduler_enabled` and `manual_start_requested` are durable; the deployment `YUKARI_NODE_AUTOPLAY=0` gate still blocks starting. The UI shows the deployment reason, and stop remains available.

`startvolume` is editable (0–100), stored in MySQL, and included only in a new queue task claim; Agent applies it once before loading that media. Request ordering flags are applied from MySQL to each new React and signed Legacy PHP reservation; they never rearrange existing requests. Legacy PHP User search/point-song remains available through its authenticated Fastify compatibility route; legacy SQLite writers and Legacy playback scheduling remain disabled in MySQL mode.

Legacy settings page exception: `/init.php` may render for inspection on authenticated GET in MySQL mode. It discards request parameters before rendering, hides the password field's stored value, disables the form, and rejects POST with 410. It is not a settings writer; React Admin remains authoritative.

Admin `/playback` is the dedicated route for the existing task-bound mpv controls and scheduler actions. Keep `/` queue controls compatible while maintaining the separate route; both call the same authenticated Fastify endpoints, never direct Agent/IPC access.

User /player may expose only sanitized, task-bound mpv controls for a confirmed formal queue task: pause/resume, seek, volume/mute, audio/subtitle track selection, bounded audio delay, and fullscreen. It must use a user session and the typed Fastify allowlist; never reveal media paths or expose stop/skip/scheduler actions to ordinary users. Admin retains queue lifecycle and scheduler authority.

Phase 24 playback recovery: Fastify/MySQL remains the sole formal queue owner. On every MySQL-mode Fastify start, recover claimed/playing tasks to uncertain and acquire the owner fence even when the deployment autoplay gate is off; this allows authenticated Agent reconciliation, not new claims. The Agent may re-adopt only after its owned mpv reports the exact configured media path actively playing/paused. A real pending EOF from that same task may complete once; missing/mismatched media becomes failed/stopped, never EOF. Admin retries only a terminal failed request after the same authenticated Agent confirms mpv idle/stopped; retry restores the original reservation to unplayed and appends an event, preserving FIFO order and the old task. Manual handling appends an Admin reason and uses the existing stopped projection without changing playtimes. Recheck is observational; network failure never means stopped. Do not bypass Agent identity, launch a second player, or change task state from the browser.

Phase 21 LAN User Web: the dedicated `user-lan` container publishes only port 8181, serves the production User Web, and proxies an exact method/path allowlist of user `/api/v1` routes. It must never proxy `/admin`, Legacy PHP, Agent/Launcher, health, or MySQL routes. Admin/PHP/API/Vite/MySQL host ports remain loopback-bound. The authenticated Windows Agent may report filtered RFC1918 IPv4 candidates for the Admin-only QR; never expose those addresses or media paths through public user status. Fastify accepts dynamic LAN Origin only from the dedicated proxy when Origin and forwarded Host match, the address is private IPv4, and the configured user port matches. User Web requests stay same-origin, retain per-browser HttpOnly sessions and CSRF markers, and never use localhost/Docker service names in browser code. Do not add Windows Firewall rules automatically; document the narrow Private-profile TCP 8181 rule if the operator's firewall blocks access.

Phase 22 connection entry: `app_setting` stores the one-instance room label, optional public HTTPS User URL and preferred `lan`/`public` mode; no new MySQL table. Public URL must be a domain HTTPS `/user/` URL and is only advertised after the Admin browser verifies the exact public nonce probe. This proves reachability from that browser only, not universal Internet availability. Custom public user Origin is accepted only while explicitly selected and only through the dedicated `user-lan` proxy marker with matching forwarded Host; Admin routes still reject it. Keep the public probe data-only and CORS `*` only on that exact probe. Public sessions get Secure cookies. Unknown LAN/proxy routes stay 404. Do not configure DNS, VPN, reverse proxy, router forwarding or firewall automatically. Room name is public metadata; switching rooms means opening another independent instance URL, not changing database tenancy. See [room entry runbook](docs/ROOM_ENTRY.zh-CN.md).

Phase 27 live comments: display nickname/selected participant are not authentication. The selected participant UUID may be remembered in browser localStorage; browser actor/session UUID remains the permission owner. `danmaku_enabled` is an optional MySQL `app_setting` key, default off when absent; Admin `/settings` explicitly controls it. Comments are short-lived bounded Fastify memory only, plain text with per-client/global limits, and are delivered only to the authenticated current Windows Agent. The Agent uses its existing persistent mpv IPC and a fixed `osd-overlay` ASS-events channel; it moves messages right-to-left by updating their positions, without relying on ASS animation timing. User text cannot provide ASS tags, IPC commands, file paths, or shell arguments. Keep the LAN nginx method/path allowlist exact. Never change queue/task/EOF state when displaying or clearing comments; never claim screen delivery until the Agent/mpv path actually accepts the overlay. Full-screen venue rendering still requires manual confirmation.

Phase 28A Web Gateway: canonical Apache/Nginx policies live under `gateway/`. Apache stays loopback-only on 8180 for Legacy PHP and local React routes. The default `user-lan` Nginx gateway publishes the configured LAN port and serves only React `/user/*` and `/admin/*`; Fastify APIs are method/path allowlisted. LAN Admin Origin is accepted only through the dedicated gateway marker with a matching private IPv4 Host/port, and every Admin API still requires its Fastify Admin session/CSRF checks. Do not proxy MySQL, Agent/Launcher, mpv IPC, Everything or arbitrary PHP paths to browsers. The optional `tunnel` Compose profile uses a separate User-only Nginx origin and Cloudflare connector; no Tunnel or public endpoint starts in the default profile. Configure tunnel token and hostname routing locally; never expose Admin through it.
